# Offline development and reconciliation

This is a procedure, not a passed report. See the [design](../../DESIGN.md) and [evidence format](../../docs/evidence/acceptance-template.md).

Use only a disposable synthetic project, isolated worktrees and private data root. Bind the exact package, source and initial versions. Assign work while online, synchronize, then stop only this product for that root.

An already assigned agent attempts connection, reports offline status and continues isolated local work with its cached authority. A new conversation without cache remains provisional: it cannot create authoritative ownership, approval or completion. Record actual host/tool behavior rather than a scripted client alone.

While one participant is disconnected, use the formal service flow after restart to change ownership or a relevant decision. Reconnect the original profile, verify identity/generation and synchronize before reconciliation. Original outbox versions must remain unchanged. Stale claims/completions become conflicts or review candidates; do not patch them with current epochs to force replay.

Interrupt reconciliation, retry and verify individual results persist without duplicate resources or lost drafts. Inject lost responses only in the disposable environment and retain original request IDs. Browser reads may recover automatically, but human writes require explicit retry with the full original payload, including optional constraints, N, designation and acceptance requirements.

Observe read-only snapshots, last-sync markers and blocked stale actions. Keep actual outbox/database/chat evidence private and use sanitized references. See A12-A16 and UX08; two fake HTTP clients cannot prove real-host outage behavior.
